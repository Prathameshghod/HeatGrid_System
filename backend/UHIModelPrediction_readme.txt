# HeatGrid — UHI Prediction

## 1. Overview

HeatGrid is a satellite-based Urban Heat Island (UHI) mapping workflow that uses Landsat imagery and a trained machine learning model to estimate thermal vulnerability across an urban area.

This version generates a UHI prediction for a **single selected acquisition date**, automatically selecting the nearest available Landsat acquisition when the requested date has no suitable imagery.

The workflow produces:
- A predicted UHI score map.
- Four vulnerability classes: Low, Medium, High, and Critical.
- GeoTIFF output.

## 2. Input Data

### Satellite imagery

The workflow retrieves data from Google Earth Engine using:

- **Landsat 8 Collection 2, Tier 1, Level 2:** `LANDSAT/LC08/C02/T1_L2`
- **Landsat 9 Collection 2, Tier 1, Level 2:** `LANDSAT/LC09/C02/T1_L2`

The script searches within 30 days before and after the requested date and selects the nearest candidate date that meets its minimum valid-pixel check.

The selected image date may differ from the requested date. The output should therefore be interpreted using the actual acquisition date printed by the script.

### Study area and date

The study area is defined using a bounding box:

```python
AOI = [min_lon, min_lat, max_lon, max_lat]
```

The requested date uses the format:

```python
TARGET_DATE = "2024-05-15"
```

The model uses imagery from the selected acquisition date only. If multiple scenes are available on that same date, the script combines those same-day scenes into a composite. It does not combine observations from different dates.

### Additional data

Elevation is obtained from the USGS SRTM Global 1 Arc-Second dataset:

`USGS/SRTMGL1_003`

## 3. Preprocessing

The workflow performs the following operations:

1. Retrieves Landsat 8/9 scenes intersecting the study area.
2. Applies cloud, cloud-shadow, cirrus, and snow masking using the `QA_PIXEL` band.
3. Converts Landsat surface reflectance bands using the Collection 2 scaling factors.
4. Converts Landsat surface temperature (`ST_B10`) to degrees Celsius.
5. Calculates spectral indices and temporal features.
6. Exports the processed raster as a GeoTIFF.

Cloud masking can leave gaps where valid observations are unavailable. The script's minimum valid-pixel check does not guarantee that every pixel is clear.

## 4. Features Used by the Model

The model is loaded from:

`uhi_model_v2.joblib`

Its expected input features are read from the saved model bundle's `features` field. The inference script builds candidate features and checks that the model's required feature names are present.

### Base features

| Feature | Description |
|---|---|
| `NDVI` | Normalized Difference Vegetation Index; indicates vegetation cover |
| `NDBI` | Normalized Difference Built-up Index; helps identify built-up surfaces |
| `MNDWI` | Modified Normalized Difference Water Index; helps identify water |
| `Elevation` | Terrain elevation from SRTM |
| `doy_sin` | Sine-transformed day of year |
| `doy_cos` | Cosine-transformed day of year |

### Engineered features

The feature builder also creates candidate features such as:

- **BUI:** built-up index minus NDVI.
- **NDVI × NDBI:** interaction between vegetation and built-up characteristics.
- **Neighborhood statistics:** local means and standard deviations for spectral indices at multiple window sizes.
- **Deviation features:** local or scene-relative differences in spectral indices and elevation.
- **Terrain slope:** estimated from elevation.
- **Distance features:** distance to areas identified as water, vegetation, built-up surfaces, or dense built-up cores.
- **Scene-relative features:** percentile ranks, robust standardized values, and scene-level summary statistics.
- **Season indicators:** one-hot indicators for summer, monsoon, post-monsoon, and winter.

The exact features used for prediction are those required by the saved model bundle, not necessarily every feature generated by the feature builder.

**Important:** the feature engineering in inference must exactly match the feature engineering used to train the model. Matching feature names alone does not guarantee matching calculations or values. Verify the inference feature builder against the original training pipeline before using the maps for research or policy decisions.

LST is exported as an auxiliary band but is not intentionally included in the model's prediction feature matrix. It can be used separately for evaluation.

## 5. Prediction and Classification

The model produces a continuous score for each valid pixel. The script clips the raw predictions to the range 0–100 and applies a scene-relative normalization to create the rescaled score map.

The default classification thresholds are:

| Class ID | Class | Score interval |
|---:|---|---|
| 0 | Low | Below 37.5 |
| 1 | Medium | 37.5 to below 62.5 |
| 2 | High | 62.5 to below 78 |
| 3 | Critical | 78 and above |

If the saved model bundle contains its own `thresholds`, those values take precedence over the defaults.

These classes represent model-derived UHI or thermal-vulnerability categories. They should not be interpreted as measured air temperature, human heat exposure, or an official heat-warning classification without additional validation.

The scene-relative normalization means scores are adjusted relative to the predictions within the selected image. Consequently, scores from different dates or cities may not be directly comparable. The thresholds should also be validated against the intended interpretation of the model score.

## 6. Hotspot Grid

The workflow aggregates pixel predictions into a nominal 300 m grid.

For each grid cell, it calculates:

- **Mean score:** mean rescaled UHI score of valid pixels.
- **Hot share:** fraction of valid pixels classified as High or Critical.
- **Hotspot flag:** true when at least 50% of valid pixels are classified as High or Critical.


## 7. Output Files

Outputs are saved under the configured `OUT_DIR`.

| Output | Description |
|---|---|
| `*_uhi_prediction.tif` | Three-band GeoTIFF containing raw score, rescaled score, and class ID |

The GeoTIFF class band uses numeric IDs 0–3. Use the class mapping above when displaying or analyzing it.

## 9. Limitations

- Landsat acquisition dates are not daily; the nearest available image may be several days from the requested date.
- Clouds and missing thermal observations can produce spatial gaps.
- Landsat surface temperature is a land-surface measurement, not near-surface air temperature.
- Scene-relative score normalization can affect comparisons across dates and cities.
- Model accuracy depends on the quality and representativeness of the training data.
- The current workflow does not automatically establish prediction accuracy against independent ground measurements or reference data.
- The nominal 300 m grid aggregation should be checked against the raster's actual georeferencing and pixel dimensions.

## 10. Recommended Validation

Before using the outputs for operational decisions:

1. Verify that inference features exactly match the model's training pipeline.
2. Check the selected acquisition date, valid-pixel coverage, and cloud gaps.
3. Compare predicted spatial patterns with Landsat surface temperature and independent reference data.
4. Evaluate score errors and classification precision, recall, and F1-score on spatially independent test data.
5. Validate the classification thresholds and normalization method before comparing different dates or cities.

## 11. Model Training

HeatGrid v2 uses **XGBoost regression** to predict a relative UHI score from multiyear, seasonal Landsat GeoTIFF composites at a nominal 30 m resolution.

- **Target:** LST-derived score normalized to 0–100 within each city-season scene.
- **Features:** NDVI, NDBI, MNDWI, elevation, BUI, spectral interactions, multiscale neighborhood statistics, terrain slope, distances to water/vegetation/built-up areas, temporal features, and season indicators.
- **Data:** Includes 6 2022-2024 data of cities (Bengaluru, Dehradun, Hyderabad, Jodhpur, Mumbai and Nagpur). Each city has 4 seasons (Monsoon, Post-Monsoon, Winter and Summer) obtained from Google Earth Engine.
- **Data filtering:** Excludes invalid LST pixels and pixels with fewer than two valid thermal observations.
- **Sampling:** Up to 40,000 pixels per scene, with observation-quality weighting.
- **Validation:** Five-fold spatial-block cross-validation using approximately 2 km geographic blocks; optional leave-one-city-out validation.
- **Evaluation:** R², RMSE, MAE, Macro-F1, Quadratic Weighted Kappa, and Critical-class recall.
- **Classification:** Converts regression scores into Low, Medium, High, and Critical classes. Thresholds can be tuned to improve Macro-F1.

**Important:** The model predicts a relative thermal score derived from land-surface temperature, not air temperature. Inference features and classification thresholds must match the training pipeline for reliable results.
